# F13 — the board editor (feud)

**Status:** plan, awaiting the gate. No code written.
**Owes:** `D19`, proposed. The editor is not in spec v1 at all — the only mention anywhere is one
line in the unratified v2 draft calling a builder "a future candidate". The spec is not edited;
`D19` records the scope change.

---

## 1. Settled with the maintainer before planning

| | Decision |
|---|---|
| **Delivery** | **Download a file.** The editor emits a validated `.json` and the one manifest line to paste. Boards still load **only** from `/games/` — no second source of content, no change to spec §6.3. |
| **Scope** | **Feud only.** Rounds, ranked answers, point values. That is the content gap for the show; jeopardy's grid and ladder, and bingo's uniform card, follow later if this earns its keep. |

**What the delivery choice costs, stated plainly so it is not a surprise later:** to use an authored
board on the live Pages site you must commit and push it. The editor cannot write to the repo — a
browser page has no such power, and giving it one would mean a server, which spec §2.1 forbids. What
it can do is make the two manual steps exact: the file, and the line.

## 2. The one design decision that matters

**The editor validates with the REAL validator, not a copy of its rules.**

`/editor/` imports `../js/validator.js` and `../js/schemas.js` directly. So "it validates in the
editor" means "it will load in the game" — the same walk, the same limits, the same `expected` /
`found` prose on the same error screen the app uses.

The alternative — the editor knowing the rules itself — is the thing that always rots. Two copies of
"a label is at most 80 characters" drift the first time one of them changes, and the failure mode is
an editor that cheerfully exports a board the engine then refuses, which is worse than no editor
because the host finds out in front of the room. Nothing about the rules is written twice.

**Consequence to accept:** the editor cannot export while the board is invalid. That is the point.

## 3. Shape

A separate page, `/editor/index.html`, which the game never loads. It is not a screen inside
`index.html`, and that is deliberate: the editor must not be able to break the engine. If the
editor is wrong, the worst case is a bad file that the validator then refuses.

**The named invariants bind here too.** No `innerHTML` / `insertAdjacentHTML` / `eval` — this is our
code, and CLAUDE.md's rule is about our code, not about the directory it happens to sit in. Zero
build, zero CDN, vanilla ES modules, SPDX header, AGPL.

**Filename discipline.** The editor proposes a filename and refuses one that
`PATTERNS.gameFile` would reject, because a name the manifest cannot hold is a file the picker can
never reach — better to say so while the host can still change it.

## 4. Tasks

**`F13-T1` — the page and the model. Foundational: delivers nothing user-visible.** *(agent)*
`/editor/index.html`, `/editor/editor.js`, the in-memory board model, and the live bind to
`validator.validateBundle`. Checkpoint: typing a board and watching the validation verdict change
from invalid to valid as the last required field is filled.

**`F13-T2` — rounds and answers.** *(agent)*
Add / remove / reorder rounds; add / remove / reorder answers within a round; the survey question
and each answer's points. Checkpoint: a three-round board authored from empty.

**`F13-T3` — export.** *(agent)*
Download the `.json`, and show the exact `games.json` line. Export is **disabled while invalid**,
with a name that says why. Checkpoint: the downloaded file drops into `/games/`, the line pastes,
and the board plays.

**`F13-T4` — open an existing board.** *(agent)*
Load any board under `/games/` through `loader.resolveGameParam` (never a raw path) and edit it.
Checkpoint: `demo-feud-rounds.json` opens, a round is edited, and the export round-trips.

**`F13-T5` — tests and mutations.** *(agent)*
Checkpoint: both browsers green, every mutation below shown failing.

## 5. Mutations planned before the code

| | Mutation | Must be caught by |
|---|---|---|
| `M23` | The editor judges validity itself instead of calling `validateBundle`, and lets an over-cap board through | an assertion authoring 13 rounds and expecting export refused |
| `M24` | The exported bytes are not the object that was validated (validate one, serialize another) | a round-trip assertion: export, re-validate the STRING, expect ok |
| `M25` | Export stays enabled while the board is invalid | an assertion on the control's `disabled` state, not on the model |
| `M26` | A filename the manifest cannot hold (`../x.json`, `x.txt`) is accepted | an assertion against `PATTERNS.gameFile` |
| `M27` | The editor reaches the DOM through `innerHTML` | the existing forbidden-API sweep, widened to `/editor/` |

`M27` exists because the sweep currently reads `js/` only. A new directory of our code is exactly
where an invariant quietly stops applying.

## 6. Risks

- **A week, and this competes with content authoring for the same hours.** If it slips, the fallback
  is hand-written JSON, which is what the show would have used anyway — so it degrades safely.
- **Scope creep toward the other two game types.** Guarded by the ratified scope above; jeopardy and
  bingo need a delta of their own.
- **The editor is a second front door to the same rules.** Mitigated by construction: it imports the
  validator rather than restating it. Any assertion that finds the editor accepting something the
  engine refuses is a P0.

## 7. Explicitly out of scope

Jeopardy and bingo authoring · themes · writing to the repo · a server of any kind · editing session
state · a board library in browser storage (that was the rejected delivery option).
