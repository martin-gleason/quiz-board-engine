# F14 — Going back a round

**Owner:** agent · **Status:** BUILT — 479/479, `M42`–`M51` run · **Milestone:** v1.0
**Delta:** `D22`, **ratified 2026-09-11 by the maintainer**

---

## Problem

A host running a multi-round board can move forward and cannot move back. `D17` made a
ranked board show one round at a time and gave it a control to advance; there is no
counterpart. The maintainer's case:

> if someone accidentally skips round 7, and they land on round 8, we would want the
> ability to go back to round 7 at the state it is at.

There is a second, quieter half. **Nothing on screen says which round is showing.** A host
who presses advance twice has no signal until they read the question — which is how the
skip happens unnoticed, and why a recovery control alone treats the symptom.

## What already works — and why this delta is small

Investigated before planning, because the shape of the fix depends on it:

| Already true | Where |
|---|---|
| `setRound` takes ANY index and clamps to `0..last` — never advance-only | `js/state.js:996` |
| Cell keys are `"<column>:<row>"`, so reveals are column-scoped | `js/validator.js:593` |
| Strikes are stored per round (`D15`) | `state.strikesFor(session, round, team)` |
| The whole board is derived from the session on every repaint | `js/app.js` `repaint()` |

So *"at the state it is at"* is **already the behaviour** — writing `currentRound` back to 6
repaints Round 7 with its reveals and its strikes intact. There is **no new persisted
state, no schema change, and no state-layer work at all.** The gap is the absence of a way
to ask for it: `onRoundNext` has no `onRoundPrev`, and the toolbar has no control.

That is worth stating plainly because it changes what the review should look at. The risk
here is not "does the state survive" — it does. The risk is in the toolbar, the keyboard,
and the contract.

## Scope, settled with the maintainer at the gate

1. **`◂ Previous round`**, beside `Next round ▸`. Absent, never inert, on any layout but
   `ranked-list` — matching `round-next` exactly.
2. **`Round N of M` in the toolbar.** Host-facing, not room-facing: it goes next to the
   round controls, not on the board, so it needs no per-theme contrast work and does not
   compete with the question.
3. **`←` / `→` bound to previous / next.** The keyboard budget goes from one key to three.
   `Next round` gains a key it does not currently have.
4. **Scores do NOT rewind.** Cells and strikes belong to a round; the score belongs to the
   game. A point awarded in the skipped-into round is corrected with the `±` buttons a host
   already uses for every other correction.

**Rejected, and why:** wrapping `Next round` at the end — the existing clamp refuses this
deliberately, because it *"would put a spent round back on the screen in front of the room
and read as a reset"*, and it makes going back one round cost eleven presses on a
twelve-round board. And rewinding scores, which needs per-round score attribution: new
persisted state, a schema change, and a new class of bug where a correction lands in the
wrong round.

## Contract change (`D22`)

`docs/plans/theme-contract.md` §2, line 241 — the `data-action` enum gains `"round-prev"`,
and the toolbar gains the round-indicator element. Both carry the same absence rule as
`round-next`.

## Tasks

- **F14-T1** — `onRoundPrev` in `app.js`, wired to `state.setRound(bundle, round - 1)`.
  Foundational; delivers nothing visible on its own.
- **F14-T2** — the `◂ Previous round` button and the theme-contract line. *Checkpoint: a
  host can return to a round and find it exactly as they left it.*
- **F14-T3** — the `Round N of M` indicator. *Checkpoint: a skip is visible when it
  happens.*
- **F14-T4** — `←` / `→`, with the guards `X` already carries. *Checkpoint: the board moves
  both ways from the keyboard without disturbing cell focus.*

## Verification — mutations named BEFORE the code, run before any row is written

| ID | Mutation | Must be caught by |
|---|---|---|
| M42 | `onRoundPrev` calls `setRound(round + 1)` — the button advances | going back from Round 2 lands on Round 1 |
| M43 | Going back CLEARS the round's cell states instead of leaving them | a returned-to round keeps every reveal it had |
| M44 | Going back reads strikes for the round it left, not the one it entered | a returned-to round shows ITS OWN strikes, not the later round's |
| M45 | The indicator prints the array index, so Round 1 reads "Round 0 of 8" | the indicator is 1-based and names the total |
| M46 | The indicator is computed once at build instead of on repaint, so it freezes | the indicator follows the board after prev AND next |
| M47 | `round-prev` renders on a bingo board, which has no rounds | a layout that is not ranked-list draws no round controls at all |
| M48 | The arrow handler drops its `ctx.board.open` / `ctx.screen` guards | an arrow press with the question overlay up does not move the board |
| M49 | The arrow handler drops `event.repeat`, so a held arrow walks the whole game | a held arrow moves exactly one round |

`M48` and `M49` are named because `X` already needed both, and adversarial review found the
`repeat` one in the shipped code — a held key ran a clone, a localStorage write and a full
repaint per tick. An arrow key is far likelier to be held than `X`.

**Open risk to probe during build, not assumed:** `←`/`→` may already mean something to a
focused `<button>` or to Tab-based cell navigation. Cells are real `<button>` elements and
get keyboard behaviour from the platform (`CLAUDE.md`), so this must be tested in all three
browsers rather than reasoned about — arrow-key semantics inside a focused control are
exactly the kind of thing Chrome, Safari and Firefox are entitled to differ on. If they
differ, the keyboard task is what gets cut, not the buttons.

## Out of scope

- A round picker for jumping to an arbitrary round. Step-by-step reaches every round; a
  picker is its own delta if long boards prove it necessary.
- Any change to scoring, the session schema, or `state.setRound` itself.
- A room-facing round display on the board.
