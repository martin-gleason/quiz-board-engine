## 1. Open questions and answers

### 1.1 Ratified by the maintainer (2026-08-16)

**Q1. License.**
→ **AGPL-3.0-or-later.** This app's entire distribution model is "fork it and host it on
your own GitHub Pages." Under plain GPL, that hosting arguably isn't distribution, so
downstream improvements could stay private. AGPL's §13 network clause closes that: anyone
who serves a modified copy to users must offer them the modified source. `LICENSE` holds
the full text; every JS file carries an SPDX header (`SPDX-License-Identifier:
AGPL-3.0-or-later`); the README carries the notice and points at the vendored MIT
reveal.js license, which is compatible as an aggregate.

**Q2. Test execution.**
→ **In-repo browser test page, exercised in both Chrome and Firefox, plus a written
Safari runbook.** `/tests/index.html` is a zero-build, zero-dependency runner: it loads
fixture JSON from `/tests/fixtures/`, drives the real `validator.js` / `errors.js` /
`renderer.js`, and prints pass/fail plus the full rendered error output for visual
inspection. A contributor re-runs it by opening one URL. The Chrome MCP and Firefox MCP
both drive that same page and the demo game end-to-end, so cross-browser parity is
verified by machine on two engines. Safari has no MCP, so `docs/runbooks/safari-manual-
test.md` is a numbered, checkbox-per-step script a human follows — the spec §9 "human
chore, tracked as such."

**Q3. Repository.**
→ **`quiz-board-engine`, public, on `github.com/martin-gleason`.** Public is required for
free GitHub Pages and is the only honest posture for AGPL work. The local working
directory keeps its current name; nothing in the code depends on either.

**Q4. Play model.**
→ **Single host screen, projected.** One browser, one operator. The host clicks a cell,
reveals the answer, and awards or deducts points with per-team controls. The board is
projected or screen-shared to players. This is what §10's "no multi-device, no
multiplayer" already implies, and it means the UI never needs a player-facing view, a
lock/turn system, or any notion of who is currently allowed to click.

### 1.2 Resolved by the planner (no maintainer input required — flagged for awareness)

**Q5. Where do schemas live, given "zero build" and "zero CDN"?**
→ Hand-written plain-object schemas in `js/schemas.js`, walked by a hand-written
validator. No AJV, no JSON Schema library — both would need a bundler or a CDN. The
schemas are keyed by `schemaVersion`, so `schemas.content[1]` is the v1 content schema.
Adding a v2 later means adding a key, never editing the v1 entry.

**Q6. How are JSON syntax errors located, given `JSON.parse` messages differ per browser?**
→ We do not parse browser error strings. Chrome says "Unexpected token } in JSON at
position 412", Firefox says "expected double-quoted property name at line 14 column 3",
Safari says something else again — parsing those is a cross-browser bug farm and directly
violates the §2.5 consistency constraint. Instead: on a `JSON.parse` throw, `errors.js`
runs its **own** minimal JSON scanner over the raw text to find the first structural
fault, and reports line/column/snippet/caret from that scan. Deterministic, identical in
all three browsers, and it is what makes the §7 hints ("there is probably an extra comma
just before this position") possible at all.

**Q7. What is the `cellStates` key format?**
→ `"<columnIndex>:<rowIndex>"`, both zero-based, matching the `"0:2"` and `"2:3"` examples
in spec §4.4. Column first. Documented in the README and enforced by the state schema's
key pattern.

**Q8. How does `valueLadder` map onto cells?**
→ By array position: `cells[i]` takes `valueLadder[i]`. A per-cell `value` always wins.
If the ladder is shorter than the cell list and a cell has no `value`, that is a
validation error, not a silent zero — a board with an invisible missing point value is
exactly the failure the error screen exists to prevent.

**Q9. Does the "no `innerHTML`" invariant bind vendored reveal.js?**
→ No, and it cannot. Reveal.js uses `innerHTML` internally; we vendor it as a reviewed,
pinned, unmodified dependency. The invariant binds **our** code and, critically, **all
paths that carry user-authored content**: no string from a game JSON file ever reaches the
DOM except through `textContent` or `createElement`. The security-check step in §6 greps
our `js/` tree for `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, and
`new Function`, and treats any hit as a build-stopping failure.

**Q10. Can the app run from `file://`?**
→ **No, and the docs must say so plainly.** ES module imports and `fetch` of local JSON
are both blocked by the browser's origin rules on `file://`. Local development and local
testing require a static server (`python3 -m http.server 8000` — already on every macOS
box, no install). This is not a spec violation: the spec's constraint is zero *build*,
not zero *server*, and the deployed artifact on GitHub Pages is still pure static files.
The README, both MCP walkthroughs, and the Safari runbook all lead with this.

**Q11. What does `layout: "ranked-list"` (Feud) actually render?**
→ One column of answer rows, ordered by descending value, each row hidden until revealed.
Revealing shows the answer text and its point value. Per spec §10 F9 this is *scoped*:
the board is a reveal surface with point values; strikes and steals are host-mediated and
not modeled in code. The host awards points using the same team scoring controls as
jeopardy. No strike counter, no steal flow — those are named v2.0 seam items.

**Q12. Keyboard control?**
→ Reveal.js's own navigation keys are disabled (`keyboard: false`) so they cannot fight
the board. We bind a deliberately small set: `Escape` closes an open cell, `Space`/`Enter`
advances hidden → revealed → answered on the open cell, and `Tab`/arrow keys move focus
across cells natively. Cells are real `<button>` elements, so keyboard and screen-reader
access come from the platform rather than from bespoke ARIA. No number-key team shortcuts
in v1 — the maintainer chose the plain projected-host model, and unlabeled hotkeys are a
usability trap for an operator running a live room.

**Q13. Session storage budget?**
→ Spec §4.4 caps retention at 10 sessions. `localStorage` gives ~5 MB; a session object
for a maxed-out 12×12 board is a few KB, so the cap is nowhere near the ceiling. On a
`QuotaExceededError` we prune the oldest session and retry once, then surface a real error
screen rather than silently losing the game in progress.

**Q14. Cache-busting on fetches (spec §7)?**
→ Append `?v=<timestamp>` to every JSON fetch and send `cache: "no-store"`. GitHub Pages
edges cache aggressively and the spec explicitly calls out edit-propagation confusion as a
documented pain point. CSS theme files are *not* cache-busted — they change rarely and
churning them costs a repaint on every load.

### D3, in full — what it costs and what it buys

Recorded at length because it was the one delta whose value was not self-evident from the
table row.

Spec §3 writes the vendor directory as a single flat line (`/vendor/  reveal.js dist files
(pinned copy)`). Read literally, the dist files sit loose in `/vendor/`. Two departures:

**The `reveal.js/` subdirectory.** A flat vendor dir has no room for a second dependency.
Add one and `reveal.css` sits beside a stranger's `styles.css` with nothing to say which
belongs to what — and reveal's own MIT `LICENSE` file becomes ambiguous about what it
covers. AGPL work must keep third-party licenses attributable to the code they license, so
one directory per dependency makes attribution structural rather than remembered.

**The provenance `README.md`.** §2.3 claims vendoring makes the app "supply-chain-safe."
That claim is unverifiable unless a reader can confirm the bytes in the repo are the bytes
upstream published. `vendor/README.md` records version, the exact tarball URL, the vendoring
date, and `shasum -a 256` per file, so anyone can re-download and compare. Absent that,
"pinned copy" means only *some* copy, from *somewhere*, at *some* time — and a tampered
vendored dependency is invisible in review, because nobody reads 112 KB of minified JS. The
file also records what is deliberately **absent** (markdown, highlight, notes plugins),
which is what turns §6.2's "the markdown plugin is never loaded" from an intention into a
structural fact: the file is not in the repo to load.

**Cost:** upgrading reveal.js is now a five-step reviewed checklist (documented in
`vendor/README.md`) rather than copying files over. That friction is the point — spec §2.3
makes vendoring a security boundary, and security boundaries should not be casually crossed.

## 3. Agent roster

Four standing roles. Every phase runs through them; no phase closes without the
adversarial pass.

### A1 — JSON Author
**Owns:** `/games/*.json`, `/gametypes/*.json`, `/themes/themes.json`, `/tests/fixtures/*`.
**Charter:** Author every data file to the letter of spec §4. Author the demo content that
the whole test matrix leans on. Author, deliberately, the *broken* fixtures — one file per
row of the §9 error matrix, each broken in exactly one way, each named for the failure it
provokes. The fixtures are as much a deliverable as the working files: an error screen with
no test case is an untested feature.
**Definition of done:** every fixture provokes exactly its intended error and no other.

### A2 — Project Architect
**Owns:** module boundaries, `index.html`, the state shape, `js/schemas.js`, README.
**Charter:** Keep the five modules honest — `loader` fetches, `validator` judges, `errors`
explains, `renderer` draws, `state` remembers. No module reaches across those lines. Own
the seam the spec names in §4.4: state is one plain serializable object so that v2.0 cloud
sync is a transport swap and nothing more. Own the schema versioning discipline.
**Definition of done:** a reader can name what each module does from its exports alone.

### A3 — JS Developer
**Owns:** `js/loader.js`, `js/validator.js`, `js/errors.js`, `js/renderer.js`,
`js/state.js`, `/themes/*.css`, `/tests/index.html`.
**Charter:** Vanilla ES modules, no build step, no dependencies beyond vendored reveal.js.
Cross-browser correct in Chrome, Firefox, and Safari. `errors.js` is heavily commented per
spec §7 — the *why* of each message class explained where the code lives.
**Definition of done:** the demo game plays end-to-end, and every error fixture produces
the right file, location, and hint.

### A4 — Adversarial Agent
**Owns:** nothing. Reviews everything.
**Charter:** four lenses, applied to every phase's output.
- **Security** — Is there any path from a JSON string to the DOM that isn't `textContent`?
  Any `innerHTML`, `eval`, `new Function`, `insertAdjacentHTML`? Does `?game=` reject
  absolute URLs, `..`, non-`.json`, protocol-relative `//evil.com/x.json`, and encoded
  traversal (`%2e%2e`)? Can a theme name escape the manifest? Is imported state trusted
  anywhere before validation?
- **Performance** — Does a 12×12 board render in one layout pass or 144? Any O(n²) scans,
  any layout thrash in the reveal animation, any listener leaked per cell instead of one
  delegated listener?
- **Usability** — Does the error screen help a person who has never seen JSON before? Is
  the board legible from the back of a room at projector contrast? Does
  `prefers-reduced-motion` actually suppress motion? Can a host recover a mis-click?
- **Readability** — Could a stranger fix a bug here without asking anyone a question?
**Definition of done:** findings are filed with a concrete failing scenario, not a
sentiment. Findings are refuted or fixed, never waved off.

## 5. Features and phases

Each phase ends at a **Gate**: the adversarial agent reviews, findings are resolved, and
only then does the next phase open.

### Phase 0 — Foundation
C6, C7, C8. Repo live, Pages serving a placeholder `index.html`.
**Gate 0:** the Pages URL loads over HTTPS.

### Phase 1 — Trust the data (F1, F2)
The validator and the error screen come *first*, before anything renders. Every later
phase gets to assume its input is already clean.
- **F1** `loader.js` (fetch, cache-bust, `?game=` guard), `validator.js` (structural +
  contract, limits, key stripping, cleaned-object output), `schemas.js`.
- **F2** `errors.js` — own JSON scanner (Q6), line/column/snippet/caret, JSON-path for
  schema faults, expected-vs-found, plain-language hints. Heavily commented.
- A1 authors `games/demo.json`, the three gametype configs, and the full broken-fixture set.
- A3 builds `/tests/index.html` in this phase — the error matrix is testable the moment
  `errors.js` exists.
**Gate 1:** every §9 error-matrix row passes in Chrome and Firefox. This is the spec's
"not done until it passes extensively" clause, and it gates everything downstream.

### Phase 2 — Draw the board (F3, F4, F5)
- **F3** `renderer.js` + reveal integration; jeopardy plays end-to-end (single host screen).
- **F4** Theming — manifest-gated CSS, documented custom-property tokens, `default` +
  `midnight`.
- **F5** Animations `flip` / `zoom` / `fade`, all respecting `prefers-reduced-motion`.
**Gate 2:** demo jeopardy board plays start to finish in both engines; zero `innerHTML` in
`js/`; 12×12 board renders without visible jank.

### Phase 3 — Remember the game (F6, F7, F10)
- **F6** `state.js` — teams created in-app, scoring UI, cell lifecycle persistence, session
  keyed by content hash, resume screen, 10-session cap with silent prune.
- **F7** Bonus randomization — uniform pick from `randomizable` cells, never `lockValue`,
  stored in state, reshuffled on new session.
- **F10** Export/import — round-trip a state file; imported state validated like any input.
**Gate 3:** refresh-resume works; export → clear storage → import restores exactly; a
hand-corrupted state file lands on the error screen, not a broken board. D3–D7 ratified.

### Phase 4 — The other two games (F8, F9)
- **F8** Bingo — uniform-grid constraint enforced, `marked` lifecycle, pattern-complete
  win detection (row / column / diagonal / full-card), `preMarked` free space.
- **F9** Feud — `ranked-list` layout per Q11, scoped to reveal + point values.
**Gate 4:** ragged bingo board fails validation with a clear message; all three game types
play; a pattern win is detected exactly once.

### Phase 5 — Ship (C9, C10, full matrix)
README, Safari runbook, full cross-browser walkthroughs on both MCP-driven engines, final
adversarial sweep across all four lenses.
**Gate 5:** every §9 requirement demonstrably passes. Hand off C11 to the maintainer.

## 6. Test matrix execution

Spec §9, made concrete. Every row is a fixture in `/tests/fixtures/` and a row in the
runner's output table.

**Error screen (mandatory, extensive):** trailing comma · missing bracket · missing quote ·
wrong type · missing required field · unknown `gameType` · missing game-type file (404) ·
future `schemaVersion` · ragged grid under bingo · oversized file (>1 MB) · over-limit
string (prompt >2,000) · over-limit label (>80) · too many columns (>12) · too many cells
(>12) · unknown theme · unknown animation · malformed imported state · ladder shorter than
cells with no per-cell value (Q8).

**Security:** `?game=` rejects `https://evil.com/x.json`, `//evil.com/x.json`,
`../../etc/passwd`, `games/../../x.json`, `%2e%2e%2fx.json`, `x.txt`, `x.json.txt`, and the
empty string. Theme name outside the manifest is refused. Source sweep for `innerHTML`,
`outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function` across `js/`.

**Cross-browser walkthrough (Chrome MCP + Firefox MCP, identical script):** load demo →
create two teams → play three cells → award and deduct points → refresh and resume →
export → clear storage → import → verify board and scores identical.

**Safari:** the same script as a numbered human runbook, `docs/runbooks/safari-manual-test.md`.

## 7. Risk register

| Risk | Severity | Mitigation |
|---|---|---|
| Browser-specific `JSON.parse` messages break §7 consistency | High | Own scanner (Q6) — never parse engine strings |
| Reveal.js fights our keyboard/layout control | Medium | `keyboard: false`, board is our DOM inside one slide; reveal handles slide mechanics only (§6.2) |
| `file://` confusion makes the app look broken to first-time forkers | Medium | Documented up front in README, runbook, and error screen copy (Q10 / D7) |
| Pages edge cache makes JSON edits look like no-ops | Medium | Cache-busting + README section, per §7 |
| Error hints become a maintenance burden as schemas grow | Low | Hints attach to error *classes*, not individual fields |
| `localStorage` quota | Low | 10-session cap, prune-and-retry, then a real error (Q13) |
