# Runbook — your pass to v1.0

**Yours. Budget ~4 hours.** Nothing in here can be done by the agent: it is either a judgement
call, a browser with no automation, or the 10% you hand-author.

This is not the open-ended study plan — that is [`learning-track.md`](learning-track.md), and it
keeps. This is the short list standing between the current build and a v1.0 you can hand to other
people. Work top to bottom; each block ends in something checked off.

| # | Block | Budget | Blocking v1.0? |
|---|---|---|---|
| 0 | Deal with the Safari transcript | 5 min | **Yes — do it first** |
| 1 | Review PR #1 and start the review log | 45 min | **Yes** |
| 2 | Safari manual pass (C11) | 60 min | **Yes** |
| 3 | Author a theme, by hand (the 10%) | 75 min | No |
| 4 | Ship it and hand it to testers | 40 min | **Yes** |

Three of the four are gates. Block 3 is the one that is actually *yours* — it is here because a
v1.0 you shipped without writing any of is a v1.0 you will not be able to maintain.

## Block 1 — Review PR #1, and start the log (45 min)

**Why this one is first.** It is the largest single diff the project will ever take in one PR
(F11 + F12 + the README, ~1,000 lines), and it is the last chance to catch something before
strangers see it. It is also the first entry in a log that does not exist yet.

### 1.1 · Read the diff the slow way (30 min)

```sh
git fetch origin
git checkout F11/startup-pickers
python3 -m http.server 8000     # then open http://localhost:8000/
```

Play with it *before* you read a line — click through the picker, pick a theme, start a board.
Form an opinion about the feature as a user first. Then read the diff, in this order:

1. `games/games.json` and the `gamesV1` schema in `js/schemas.js` — small, and they establish the
   shape everything else follows.
2. `js/loader.js` → `fetchManifests()`.
3. `js/app.js` → the boot fork and `showStartup()`. **This is the file to spend your time on.**
4. `js/renderer.js` → `renderStartupScreen()`.
5. `themes/default.css` and the README last.

**The question worth carrying through all five:** *the picker rebuilds a `?game=` parameter and
sends it back through `loader.resolveGameParam` instead of just fetching the filename it already
has.* That looks like a pointless detour. Decide for yourself whether it is one. If you can say out
loud why it is not, you understand the security model of this app.

Two more worth forming a view on, because they are decisions rather than mechanics:

- The theme preference lives under its own `localStorage` key instead of in the session record.
  What does that cost, and is the cost worth it?
- The startup screen mounts **outside** `.reveal`. Find the comment saying why. Do you buy it?

### 1.2 · Create `docs/pr-review-log.md` and write the first entry (15 min)

`CLAUDE.md` has required this file since day one and it has never existed. Create it, write one
entry for PR #1, and commit it straight to `main` after you merge:

```sh
git commit -m "docs(quiz-board-engine): add PR #1 review-log entry"
```

Format is deliberately open — do not template it. What makes an entry useful in six months is
what you *thought*, not what changed; the diff is already in git. One honest sentence about
something you did not follow is worth more than a paragraph restating the summary.

- [ ] Diff read end to end
- [ ] PR #1 merged (rebase-and-merge — no squash)
- [ ] `docs/pr-review-log.md` exists with entry #1, committed to `main`

## Block 2 — The Safari pass, C11 (60 min)

**Why it cannot be automated:** there is no Safari MCP and no Marionette equivalent. Chrome and
Firefox are both driven headlessly and both report 370/370; Safari is checked by a person or it is
not checked. The spec requires all three to behave identically, so this is a real gate.

Follow [`safari-manual-test.md`](safari-manual-test.md) exactly. It is numbered; do not skim it.

**Do not skip the first step.** Safari → Develop → Empty Caches, *before* you load anything. The
runbook explains why at length: it has already produced one false bug report on this project, where
Safari ran the previous build's `js/app.js` against the current build's JSON and the feature simply
appeared to be missing. `⌘R` is not enough.

What you are actually looking for, in order of likelihood:

1. **Caret alignment on the error screens.** Safari's monospace metrics differ from Chrome's, and
   the caret under a JSON syntax error is the single most likely place for a Safari-only visual
   defect. Check three different error screens, not one.
2. **The assertion count.** It must read exactly `PASS 370/370`. A *different* number that still
   says PASS is a cross-browser defect, not a pass.
3. **The startup picker**, which is new since the last Safari pass and has never been seen in it.
4. Grid geometry and theme rendering at projector size.

Expect exactly one console error on a clean run — the negative-path import test. The runbook
quotes it verbatim. Its *absence* would be the defect.

- [ ] Runbook completed, Safari version and date recorded in it
- [ ] `PASS 370/370`
- [ ] Any Safari-only defect filed as an issue before tagging

## Block 3 — Author a theme, by hand (75 min)

**This is the 10%.** The dial says the agent authors and you review; theming is the declared
exception, and this is where you spend it. Everything else in this runbook is a checkbox — this
block is the one where you write something.

It is deliberately not blocking v1.0. Ship without it if the four hours run out. But do it before
you invite people to *make* boards, because the first thing anyone will ask for is a different look,
and you should know that path from the inside before you promise it.

**The task.** One new theme file, registered, playable. Not a variation on `midnight` — pick a
constraint and follow it somewhere the shipped five do not go.

**Read first (30 min).** [`theme-contract.md`](../plans/theme-contract.md) §4 (the token
reference), §5 (non-negotiables), §6 (what a theme cannot do). Then open `themes/civic.css`, which
is the most heavily commented of the donated five, and read it beside the contract.

**Then write it (45 min).**

```sh
cp themes/civic.css themes/yourname.css   # start from a commented one, not from default.css
```

1. Change only colour tokens on the first pass. Register it in `themes/themes.json`, point a game
   file's `theme` at it, load the board.
2. Now make `answered` read as spent using **lightness and texture only** — no hue change. Check it
   in greyscale (System Settings → Accessibility → Display → Color Filters → Grayscale). If you
   cannot tell spent from unplayed, you have just learned first-hand why the contract requires it.
3. Compute the contrast ratio for every text-on-background pair and write each number into a
   comment beside the colour, the way the donated themes do. Any pair under AA: change the colour,
   not the comment.
4. Run the suite. The `themes` group audits every registered theme automatically — SPDX header, no
   external requests, no invented tokens, no dead classes. It will tell you which of those you got
   wrong, which is faster than me telling you.

**The trap to expect.** A token the base layer does not define is *inert* — your rule does nothing
and there is no error. If a colour will not take, that is the first thing to check.

- [ ] Theme file written, SPDX header present, registered in `themes/themes.json`
- [ ] Greyscale check passed
- [ ] Contrast ratios computed and commented
- [ ] Suite green

**Ask for a concept, not a snippet.** "Why is my `--cell-answered-bg` doing nothing?" gets you the
inert-token rule and you will never hit it again. "Write the rule" gets you a line you will not
recognise in three weeks.

## Block 4 — Ship it, and hand it to testers (40 min)

### 4.1 · Merge and tag

Pages is already live and deploys from `main`, so merging *is* releasing.

```sh
# after PR #1 is merged and the review-log entry is committed
git checkout main && git pull
git tag -a v1.0.0 -m "v1.0.0 — first shareable release"
git push origin v1.0.0
```

Then wait two or three minutes and load
<https://martin-gleason.github.io/quiz-board-engine/> in a browser that has never seen it.
Pages caches at its edge; a stale first load is normal and is not a bug.

### 4.2 · Check it as a stranger would (15 min)

On the live site, not on localhost — this is the first time the app runs anywhere but your laptop:

- [ ] The picker lists three boards by name
- [ ] Each of the three boards opens and plays
- [ ] A theme override applies and survives a reload
- [ ] Export downloads a file; import restores it
- [ ] DevTools → Network shows **zero** requests to any host that is not `github.io`

That last one is constraint 3, and the live site is the only place it can honestly be checked.

### 4.3 · Tell testers what you want to know

Send the link with the two demo paths spelled out — a stranger who lands on the picker will not
guess that `?game=` exists, and will not think to try bingo. Ask for something specific:

> Play one board start to finish with real people in the room. Tell me the moment you had to stop
> and think about the interface instead of the game.

That question gets you usable answers. "Any feedback?" gets you silence or praise, and neither is
worth a release.

- [ ] Tag pushed, live site verified cold
- [ ] Link sent with a specific question attached
